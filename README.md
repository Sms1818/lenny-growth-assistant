# Lenny Growth Assistant

A grounded conversational assistant that answers product and growth questions using Lenny's Podcast and Newsletter as its knowledge base. The system retrieves relevant source material, generates answers, and validates them against those sources before returning a response. It also generates Markdown and HTML artifacts—including Ship 30 for 30-style essays—from the same grounded knowledge.

---

## Features

- **Grounded Q&A**: Answers product and growth questions strictly from the Lenny knowledge base. Cites sources inline (`[1]`, `[2]`) and declines to answer when the sources are insufficient.
- **Multi-turn sessions**: Each conversation is a persistent session with full message history. Follow-up questions inherit context from previous turns.
- **Source citations**: Every assistant response records the retrieved knowledge chunks and exposes titles, source type (podcast or newsletter), guest name, source URL, YouTube URL, and timestamp range where applicable.
- **Three provider modes**: Auto, Local (Ollama), and Cloud (OpenAI via Pi), switchable per-request from the UI.
- **Artifact generation**: Produces Markdown and complete HTML documents anchored to the same retrieval and grounding pipeline as chat.
- **Ship 30 for 30 skill**: A dedicated generation skill with an encoded writing contract—approximately 1,250 words, strong hook, narrative progression, skimmable structure, and concrete takeaway—grounded in Lenny source material.
- **In-app artifact viewer**: A side panel for Markdown (rendered) and HTML (sandboxed iframe) artifacts. Supports opening artifacts in a new browser tab.
- **Persistent storage**: PostgreSQL (with the pgvector extension) stores sessions, messages, artifacts, source references, and knowledge chunks.
- **Reproducible deployment**: Docker Compose starts PostgreSQL, the backend, and the frontend. The ingest step is a separate Compose profile.

## Architecture

```
Browser (React / Vite)
        |
        | HTTP (JSON)
        v
FastAPI backend  (Python 3.12, uvicorn, asyncpg)
  |         |              |
  |    PostgreSQL      Ollama (always used for embeddings)
  |    + pgvector         |
  |                  nomic-embed-text  (embeddings — all modes)
  |                  llama3.2:3b       (chat generation — Local/Auto)
  |                  qwen3:4b-instruct (artifact generation — Local)
  |
  Pi Coding Agent CLI  ─────────────────> OpenAI (cloud generation — Cloud/Auto artifacts)
```

**Request flow for a chat message:**

1. The frontend sends `POST /sessions/{id}/messages` with `content` and `provider_mode`.
2. The backend embeds the query (plus up to three prior user turns for context) via Ollama's `/api/embed`.
3. The retrieval layer runs a hybrid semantic + lexical search with Reciprocal Rank Fusion (RRF) against the pgvector index.
4. The top-5 chunks are assembled into a numbered source context block.
5. An agent client (Ollama HTTP or Pi CLI) generates an answer using the context and the last six conversation turns as history.
6. The grounding validator scans the answer for unsupported quoted phrases and unsupported acronym expansions; it attempts to auto-correct and, if issues remain after a retry, returns a fixed refusal message.
7. The user message, assistant message (with `model_provider`, `model_name`, `source_chunk_ids`), and session timestamp are committed to PostgreSQL.
8. The response includes the assistant message and a `sources` array.

## How Grounded Answers Work

### Ingestion

Source documents (Markdown files with YAML front matter) are parsed by `backend/app/knowledge/parser.py`. Podcast transcripts are split into speaker turns with timestamps; newsletter documents are treated as prose.

Chunking (`backend/app/knowledge/chunker.py`) produces:

- **Podcast chunks**: ~1,200 characters, aligned to speaker-turn boundaries. Each chunk carries `start_timestamp` and `end_timestamp`.
- **Newsletter chunks**: ~1,500 characters, aligned to paragraph boundaries.

Oversized units are split at sentence boundaries before the character ceiling is applied.

Embeddings are generated by calling Ollama's `/api/embed` endpoint with `nomic-embed-text` (768-dimensional vectors). Chunks are sent to Ollama in batches of 32 (configurable via `--batch-size`).

The `KnowledgeDocument` record stores title, guest, `published_at`, `source_url`, `youtube_url`, `source_type`, `word_count`, and a SHA-256 content hash. The `KnowledgeChunk` record stores the text, the 768-dimensional vector, optional timestamps, and an approximate token count.

### Refresh behavior

Running the ingest script again on a previously indexed file is a no-op if the SHA-256 content hash is unchanged. If the hash differs, the document record is updated and all its chunks are deleted and re-embedded. Individual document failures are logged to stderr and counted, but do not stop the rest of the run.

### Retrieval

`backend/app/knowledge/retrieval.py` runs a hybrid search in a single database round trip:

1. **Semantic**: cosine distance via pgvector, top candidates selected.
2. **Lexical**: PostgreSQL `to_tsvector` / `to_tsquery` full-text rank (`ts_rank_cd`), top candidates selected.
3. **Fusion**: Reciprocal Rank Fusion (RRF, k=60) merges both candidate sets.
4. **Metadata boost**: A small additive bonus (`0.01`) is applied if the query text contains the episode guest's full name or a significant title keyword.

The final list is sorted by composite score then similarity, and the top-N results are returned.

### Generation and grounding validation

Retrieved chunks are formatted as a numbered source block (`[1]`, `[2]`, …). The system prompt instructs the model not to quote text verbatim unless those exact words appear in a source, not to expand an acronym unless the supplied sources define it, and to cite every factual claim with a source number. These are model-level instructions, not guarantees.

After the model responds, the grounding validator (`backend/app/assistant/grounding.py`) applies two deterministic pattern-based checks:

- **Unsupported quotes**: Any string of 12+ characters in quotation marks (straight or curly) that does not appear verbatim in the source context.
- **Unsupported acronym expansions**: Any `ACRONYM (expansion)` or `expansion (ACRONYM)` pattern where the pairing is not found in the source context.

If issues are found, the cleaner first tries to auto-correct them (stripping the parenthetical or removing the quotes). If any issues survive, the model is sent a correction prompt with the issues listed explicitly. If issues remain after the retry, the answer is replaced with a fixed refusal message.

### Source traceability

Each assistant message persists `source_chunk_ids` (a JSONB array) in the database. When the message list is fetched, the source service resolves those IDs back to full document metadata (title, type, guest, URLs, timestamps) and returns them in the `sources` array.

## Knowledge Base and Ingestion

The corpus is Lenny's Podcast transcripts and Newsletter articles in Markdown format with YAML front matter. Source files live under `data/podcasts/` and `data/newsletters/`. These directories are not gitignored (`.gitignore` only excludes `data/raw/` and `data/processed/`); they are simply empty in this repository and must be populated before running ingestion.

**Front matter fields used:**

| Field | Purpose |
|---|---|
| `type` | `podcast` or `newsletter` |
| `title` | Document title |
| `guest` | Podcast guest name (optional) |
| `published_at` / `date` | Publication date |
| `source_url` / `url` | Canonical link |
| `youtube_url` | YouTube episode link (optional) |
| `description` | Short summary (optional) |

**Embedding model:** `nomic-embed-text` via Ollama, 768-dimensional vectors stored as `pgvector` `vector(768)` columns.

**Running ingestion:**

```bash
# Via Docker Compose (recommended — uses the same DATABASE_URL as the backend)
docker compose --profile tools run --rm ingest /data

# Directly against a running local backend stack
cd backend
python scripts/ingest_knowledge.py /path/to/data --batch-size 32
```

The script prints per-document status (`INSERTED`, `UPDATED`, `SKIPPED`, `FAILED`) and exits with code 1 if any documents failed.

## LLM Provider Modes

The provider mode is set per request from the frontend `Provider` toggle (Auto / Local / Cloud) or sent directly in the API payload as `provider_mode`.

### Auto (default)

- **Chat**: Uses the local Ollama model (`llama3.2:3b` by default). If local generation fails with a timeout or runtime error, and `CLOUD_FALLBACK_ENABLED=true`, the request is retried with the configured cloud provider. If `CLOUD_FALLBACK_ENABLED=false` (the default), a failure is returned immediately without any cloud retry.
- **Artifacts and Ship 30**: Routes directly to the cloud provider (`gpt-5.4-mini` by default via OpenAI). No local model is attempted. If `OPENAI_API_KEY` is not set, the request fails with HTTP 503 before generation begins.

### Local

Sends all generation—chat and artifacts—to Ollama. Chat uses `AGENT_MODEL` (`llama3.2:3b`); artifacts use `ARTIFACT_MODEL` (`qwen3:4b-instruct`). Cloud fallback is disabled in Local mode even if `CLOUD_FALLBACK_ENABLED=true`.

### Cloud

Sends all generation directly to the configured cloud provider (`CLOUD_PROVIDER`, `CLOUD_MODEL`). Ollama is still used for retrieval embeddings in this mode; only generation is routed to the cloud. Requires `OPENAI_API_KEY` to be set; returns HTTP 503 if the key is absent.

### Pi Coding Agent

Cloud generation is executed via the Pi Coding Agent CLI (`@mariozechner/pi-coding-agent`, installed in the backend Docker image as `pi`). Pi is invoked as a subprocess with `--no-tools --no-session --mode json --print`, and the backend parses its JSONL output. The Pi agent model registry is configured at build time via `backend/docker/pi-models.json`, which maps the `ollama` provider to `host.docker.internal:11434`.

Ollama chat uses a direct HTTP call to Ollama's OpenAI-compatible `/v1/chat/completions` endpoint; Pi is not used for local chat.

### Visible provider in responses

Every API response for chat and artifacts includes `provider_mode`, and every persisted message stores `model_provider` and `model_name`. The frontend displays the current mode via the `Provider` toggle in the header.

## Ship 30 for 30 Skill

Ship 30 for 30 is implemented as a dedicated skill in `backend/app/assistant/skills/ship30.py`, not as a modified version of the general chat prompt.

### Writing contract encoded in the skill

The `SHIP30_SYSTEM_PROMPT` encodes the following requirements explicitly:

- Approximately 1,250 words (practical target 1,100–1,350).
- One strong, specific H1 headline.
- A compelling opening hook.
- Clear narrative progression rather than a list of notes.
- Skimmable Markdown with meaningful headings and short, varied paragraphs.
- Bullets only where they improve clarity; selective bold emphasis.
- A concrete and useful closing takeaway.
- Inline source citations (`[1]`, `[2]`) for every factual claim.

The generation prompt separately restates every structural requirement so the model receives them twice: once in the system prompt and once in the user prompt.

### Structural validation

After generation, `validate_ship30_structure` checks:

- Word count is between 1,000 and 1,500 (bounds differ slightly from the target range to tolerate minor variance).
- The first non-empty content line starts with `# ` (H1 headline).
- At least one inline citation (`[N]`) is present.

If structural issues or remaining grounding issues are present, the API returns HTTP 422 with a structured error listing both `grounding_issues` and `structure_issues`.

### Retrieval behavior

Ship 30 retrieves 8 chunks (versus 5 for chat). If the topic is self-contained (contains no pronouns or references implying prior context), retrieval uses the topic alone. If the topic references prior conversation, the retrieval query is expanded with the last three user turns.

### Provider behavior

In Auto mode, Ship 30 uses the cloud model (same as artifacts). In Local mode, Ship 30 uses `ARTIFACT_MODEL` via Pi (not `AGENT_MODEL`). In Cloud mode, it uses the configured cloud model. The skill does not use `OllamaAgentClient`; it always invokes Pi.

## Artifact Generation and Security

Artifact generation is a separate API endpoint from chat. Supported types are `markdown` and `html`.

### Generation flow

Artifact generation retrieves 5 chunks from the knowledge base and runs the same grounding pipeline as chat. The system prompt for each type differs:

- **Markdown**: Output must start with one H1, use standard Markdown elements, and not be wrapped in a code fence.
- **HTML**: Output must be a complete document (`<html>`, `<head>`, `<style>`, `<body>`). Only embedded CSS is permitted. JavaScript, `<script>`, `<iframe>`, `<object>`, `<embed>`, and inline event handlers are explicitly forbidden in the system prompt.

### Backend validation

Before any artifact is persisted, `validate_html_artifact` scans the generated HTML using the following forbidden patterns:

| Pattern | Blocks |
|---|---|
| `<script\b` | Script elements |
| `\bon\w+\s*=` | Inline event handlers (`onclick`, `onload`, etc.) |
| `javascript\s*:` | JavaScript URIs |
| `<iframe\b` | Iframes |
| `<object\b` | Object embeds |
| `<embed\b` | Embed elements |

If any pattern matches, the artifact is rejected with HTTP 422 and the generation is not persisted.

For Markdown artifacts, validation checks for non-empty content and the presence of an H1.

### Grounding validation for HTML

`validate_html_grounding` extracts visible text from the HTML (skipping `<script>`, `<style>`, and `<noscript>` content) and runs the same quote and acronym checks as the text grounding validator. The HTML-aware cleaner (`_HtmlGroundingCleaner`) operates on text nodes only and does not modify tag attributes, preserving `aria-label` and similar non-content strings.

### In-app artifact viewer

The `ArtifactViewer` component renders Markdown with `react-markdown` (with GFM support) and HTML in an `<iframe sandbox="">` — the empty `sandbox` attribute grants no permissions to the iframe, blocking script execution, same-origin access, form submission, popups, and top-level navigation. Generated HTML is never inserted into the main document DOM.

### New-tab viewing

The "Open in new tab" button creates a `Blob` URL from the artifact content (`URL.createObjectURL`) and opens it with `window.open(..., "noopener,noreferrer")`. For HTML artifacts, the raw generated HTML is used. For Markdown, `marked.parse` converts the content to HTML first, and a minimal stylesheet is applied. The Blob URL is revoked after five minutes. The `noopener,noreferrer` flags prevent the opened tab from accessing the opener window via `window.opener`. Note that the `sandbox=""` isolation described above applies specifically to the in-app iframe panel, not to the new-tab view. The new tab relies on the backend's pattern-based validation to reject forbidden HTML constructs before they are ever stored.

## Persistence

The database schema uses four application tables, managed by Alembic migrations. The backend runs `alembic upgrade head` automatically at startup before starting uvicorn.

| Table | Purpose |
|---|---|
| `sessions` | UUID primary key, optional title, JSONB `user_metadata`, `created_at`, `updated_at` |
| `messages` | UUID PK, `session_id` FK, `sequence_number` (unique per session), `role`, `content`, `model_provider`, `model_name`, JSONB `source_chunk_ids`, `created_at` |
| `artifacts` | UUID PK, `message_id` FK, `title`, `artifact_type`, `content` (full text), `created_at` |
| `knowledge_documents` | UUID PK, `source_type`, `filename` (unique), title, guest, `published_at`, URLs, `word_count`, `content_hash` (SHA-256), JSONB `source_metadata` |
| `knowledge_chunks` | BigInteger PK, `document_id` FK, `chunk_index`, `content`, timestamps, `token_count`, `embedding` (vector(768)) |

Sessions cascade-delete their messages; messages cascade-delete their artifacts; documents cascade-delete their chunks.

The session title is set automatically from the first message content (stripped of artifact-type prefixes such as "Create html artifact:") and truncated to 60 characters. It can also be updated via `PATCH /sessions/{id}`.

## Quick Start

### Prerequisites

- Docker and Docker Compose
- [Ollama](https://ollama.ai) installed and running on the host machine
- The Lenny corpus files in `data/podcasts/` and `data/newsletters/` (not populated in this repository; see Knowledge Base and Ingestion)

### 1. Pull the required Ollama models

```bash
ollama pull nomic-embed-text
ollama pull llama3.2:3b
ollama pull qwen3:4b-instruct
```

`nomic-embed-text` is required for ingestion and every retrieval query. `llama3.2:3b` is used for Auto and Local chat. `qwen3:4b-instruct` is used when generating artifacts in Local mode.

### 2. Configure environment variables

```bash
cp backend/.env.example backend/.env
```

Edit `backend/.env` if you want to use Cloud mode or enable Auto-chat cloud fallback. The minimum required change is adding `OPENAI_API_KEY` if you plan to use Cloud mode or Auto-mode artifacts.

```bash
cp frontend/.env.example frontend/.env
```

The frontend default (`VITE_API_BASE_URL=http://localhost:8000`) works without changes for local Docker Compose.

### 3. Start the stack

```bash
docker compose up --build
```

This starts PostgreSQL, applies Alembic migrations, and starts the backend and frontend. The backend is available at `http://localhost:8000`; the frontend at `http://localhost:5173`.

### 4. Ingest the knowledge base

Place your corpus files in `data/podcasts/` and `data/newsletters/`, then run:

```bash
docker compose --profile tools run --rm ingest /data
```

Ingestion must complete before the assistant can answer questions. Subsequent runs skip files whose content hash has not changed.

### 5. Verify health

```bash
curl http://localhost:8000/health
```

Expected response:

```json
{"status": "ok", "service": "Lenny Growth Assistant", "environment": "development"}
```

### 6. Open the UI

Navigate to `http://localhost:5173`.

## API

The FastAPI application exposes interactive documentation at `http://localhost:8000/docs` (Swagger UI) and `http://localhost:8000/redoc` (ReDoc).

### Endpoint groups

| Group | Prefix | Description |
|---|---|---|
| Health | `/health` | `GET /health` — returns `{"status": "ok", "service": ..., "environment": ...}` |
| Sessions | `/sessions` | CRUD for conversation sessions |
| Messages | `/sessions/{id}/messages` | List and send chat messages |
| Artifacts | `/sessions/{id}/artifacts` | Generate Markdown/HTML artifacts |
| Ship 30 | `/sessions/{id}/artifacts/ship30` | Generate Ship 30 for 30 essays |
| Artifact fetch | `/artifacts/{id}` | Retrieve a persisted artifact by ID |

### Key request/response shapes

**Send a chat message** — `POST /sessions/{session_id}/messages`

```json
{
  "content": "How did Duolingo reignite its user growth?",
  "provider_mode": "auto"
}
```

Response includes `user_message`, `assistant_message` (with `model_provider` and `model_name`), `sources` (array of chunk metadata), and `provider_mode`.

**Create an artifact** — `POST /sessions/{session_id}/artifacts`

```json
{
  "artifact_type": "html",
  "instruction": "Create a one-page brief on Duolingo's retention strategy",
  "provider_mode": "auto"
}
```

**Create a Ship 30 essay** — `POST /sessions/{session_id}/artifacts/ship30`

```json
{
  "topic": "The retention lesson every growth team should take from Duolingo",
  "provider_mode": "auto"
}
```

Errors from artifact and Ship 30 endpoints are structured:

```json
{
  "detail": {
    "code": "artifact_generation_failed",
    "message": "...",
    "grounding_issues": [...],
    "validation_issues": [...]
  }
}
```

## Observability and Resilience

### Structured logging

`backend/app/core/logger.py` defines `log_event(event_name, **kwargs)`, which writes a JSON object to stdout with a UTC timestamp and the event name. Key events logged:

| Event | When |
|---|---|
| `retrieval_complete` | After each knowledge search, with `chunks_found` and `query_length` |
| `grounding_retry_used` | When the first generation attempt has grounding issues |
| `grounding_failed` | When grounding issues persist after the correction retry |
| `generation_started` | At the start of artifact/Ship 30 generation, with plan details |
| `generation_success` | On successful generation, with `provider` |
| `local_generation_failed` | When local generation raises `TimeoutError` or `RuntimeError` |
| `falling_back_to_cloud` | When Auto mode triggers cloud fallback |
| `cloud_provider_unavailable` | When cloud mode is requested but `OPENAI_API_KEY` is not set |
| `embedding_service_unavailable` | When Ollama is unreachable during embedding |
| `database_error` | On unhandled `SQLAlchemyError`, with error class name |

### Error handling

| Condition | HTTP status | Structured error code |
|---|---|---|
| Ollama unreachable during embedding | 503 | `embedding_unavailable` |
| Ollama returns an error status during embedding | 502 | `embedding_failed` |
| Database error | 503 | `database_unavailable` |
| Cloud key missing when cloud mode requested | 503 | `cloud_provider_unavailable` |
| Local generation timeout (Local mode) | 504 | `artifact_generation_timeout` |
| Local generation failure (Local mode) | 502 | `artifact_generation_failed` |
| Cloud generation timeout | 504 | `cloud_generation_timeout` or `cloud_fallback_timeout` |
| Artifact fails grounding or structure validation | 422 | `artifact_generation_failed` |
| Session or artifact not found | 404 | _(FastAPI default)_ |

### Empty retrieval

If the knowledge search returns no chunks, the assistant returns a fixed message: "I couldn't find enough relevant information in the Lenny knowledge base to answer that." No generation is attempted. Ship 30 and artifact endpoints return HTTP 422 with `insufficient_source_material` if retrieval is empty.

### Timeouts

Ollama HTTP calls use `httpx` with a 120-second timeout for chat and 300-second timeout for artifacts (configurable). Pi subprocess calls use `asyncio.wait_for` with the same configured timeouts; the subprocess is killed on timeout. The database connection is released before long-running model generation begins (see the `await db.rollback()` call in the artifact routes) to avoid holding idle connections during inference.

### Frontend resilience

The frontend checks `/health` on startup and displays a "Disconnected" badge if the backend is unreachable. API errors are surfaced as inline banners. Generation in progress is tracked with a live elapsed-time counter.

## Troubleshooting

**Backend fails to start with "database is unavailable"**
PostgreSQL may still be initializing. Docker Compose uses a healthcheck (`pg_isready`) with 10 retries and a 5-second interval before marking the service healthy. The backend `depends_on: condition: service_healthy` waits for this check. If the issue persists, run `docker compose logs postgres`.

**Embedding fails with 503 during ingestion or a query**
Ollama is not reachable at `OLLAMA_BASE_URL`. Verify Ollama is running (`ollama list`) and that the backend can reach it. Inside Docker, the backend connects to `host.docker.internal:11434`.

**Ollama model not found error**
Run `ollama pull <model-name>` for each required model. The ingest container and backend container both need `nomic-embed-text`. Chat needs `llama3.2:3b`. Local artifact generation needs `qwen3:4b-instruct`.

**Cloud mode returns 503 with `cloud_provider_unavailable`**
`OPENAI_API_KEY` is missing or empty. Set it in `backend/.env` and restart the backend container.

**Artifact or Ship 30 returns 422**
The generated output did not pass grounding or structural validation after auto-correction and a correction retry. Rephrase the instruction or switch to Cloud mode, which typically produces higher-quality output.

**Pi agent fails with non-zero exit code**
Verify the `pi` binary is installed in the container (it is installed via `npm install -g @mariozechner/pi-coding-agent@0.73.1` in the backend Dockerfile). The Pi model registry at `/root/.pi/agent/models.json` is copied from `backend/docker/pi-models.json` at build time and maps the `ollama` provider to `host.docker.internal:11434`.

**Frontend shows "Unable to reach the backend"**

## Extending the System

### Adding another LLM provider

1. Add a new agent client class to `backend/app/assistant/agent.py` following the `OllamaAgentClient` pattern (implement `async def generate(self, prompt, *, system=None) -> AgentResponse`).
2. Update `resolve_provider_plan` and `create_agent_client_for_plan` in `backend/app/assistant/provider.py` to handle the new provider name.
3. Add any required API key to `Settings` in `backend/app/core/config.py` and to `.env.example`.
4. Update `build_agent_environment` if the provider needs credentials injected into the subprocess environment.

### Adding another knowledge source

1. Add the new source type to `backend/app/knowledge/parser.py` (front matter field `type`).
2. Add a corresponding chunking function in `backend/app/knowledge/chunker.py` and extend `chunk_document`.
3. Add the new type to the `source_type` validation in `backend/app/knowledge/ingestion.py`.
4. Place documents in a new subdirectory under `data/` and update the glob patterns in `backend/scripts/ingest_knowledge.py`.

### Adding another artifact or content skill

1. Create a new file under `backend/app/assistant/skills/` following the patterns in `artifacts.py` or `ship30.py`. Implement a `generate_*` coroutine that accepts an instruction, conversation history, and an optional `agent_client`.
2. Add an API route in `backend/app/api/routes/` (or extend `artifacts.py`) and expose a new endpoint.
3. Wire any new structural validation and wire the new route in `backend/app/main.py`.

### Adding another embedding model

1. Update `EMBEDDING_MODEL` and `EMBEDDING_DIMENSIONS` in `.env` and in the `ingest` service environment in `docker-compose.yml`.
2. Re-run ingestion to regenerate all embeddings under the new model.
3. Update `Vector(768)` in `backend/app/db/models.py` if the new model produces different dimensions, and create an Alembic migration to alter the column.

## Design Decisions and Trade-offs

**Local-first for chat, cloud for artifacts.** Conversational answers need to be quick; local models provide this. Artifacts and Ship 30 essays require higher output quality and longer outputs where latency matters less, so Auto mode routes them to cloud. Local mode gives evaluators and developers a fully offline path.

**Pi Coding Agent as the cloud execution layer.** Pi wraps cloud provider APIs in a consistent subprocess interface with JSON output. This avoids adding provider-specific SDKs as Python dependencies. Pi is installed in the backend Docker image at build time. For local Ollama chat, the backend calls Ollama's HTTP API directly to avoid the Pi subprocess overhead.

**Hybrid retrieval with RRF.** Semantic search alone misses exact entity matches (episode guest names, specific acronyms). Lexical search alone misses paraphrase matches. RRF with a k=60 smoothing constant combines both without requiring manual weight tuning. A small metadata boost rewards chunks from episodes whose guest name or distinctive title tokens appear in the query.

**Grounding before persistence.** The grounding validator runs synchronously before the assistant message is written to the database. This means only validated answers are stored. A single auto-correction pass handles the most common model failure modes (unsupported quotes and acronym expansions) without user intervention.

**HTML isolation via empty sandbox.** The `<iframe sandbox="">` attribute with no token values grants no permissions to the iframe: scripts cannot execute, same-origin access is blocked, form submission is prevented, popups are blocked, and top-level navigation is disallowed. The tradeoff is that generated HTML cannot use JavaScript, which is also enforced server-side by the pattern-based validator. External resource loading in the in-app iframe is a browser-level concern and is not independently blocked by `sandbox=""` alone; the backend validation prevents forbidden constructs such as `<script>`, inline handlers, and `javascript:` URIs from being stored in the first place.

**Alembic for schema management.** The backend runs `alembic upgrade head` at startup, so there is no separate migration step for evaluators. The three migration files in `backend/migrations/versions/` establish the initial schema, add `sequence_number` to messages, and add `user_metadata` to sessions.

**No streaming.** The backend returns complete responses synchronously. This simplifies the grounding validation pipeline (which needs the full response before it can check anything) at the cost of a longer wait for the first token. A generation elapsed-time counter in the frontend provides feedback during long runs.
